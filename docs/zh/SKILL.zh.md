# tasteskill v2

模型构建出的页面，通常看起来像它见过的所有页面的平均值：一个跨三行的居中标题，标题上方一个小标签，一排图标卡片，一层柔和渐变，几条细线和一行等宽字体说明。其中没有任何一处是错的，也没有任何一处是被决定过的。

本技能用决策替换这些默认值，方式有四种：

1. **脚本发牌给出方向，你在其中选择。** 被要求凭空发明一种外观时，模型每次都会挑中该品类的默认样式。`scripts/draw.mjs` 会从二十个经过研究的方向中发出三个；你选择那个能承载主题自身想法的方向，随后脚本从一份由 247 个真实站点提炼而来的库中，发出该方向的字体系统、配色、首屏与分区构图。
2. **想法来自主题本身。** 在这项研究中，最好的站点与那些被遗忘的站点之间的差别，在于取自事物本身的概念，而不是样式。
3. **一套没有多余装饰的固有风格**，由 `scripts/inspect.mjs` 在真实浏览器中测量，因此这些规则是被检查的，而不是被期望的。
4. **你要看你做出来的东西。** 三个宽度的截图，一份评审评分表，修正，再看一次。

一条在测试中学到的警告。移除装饰只是工作的一半；一个失去了标签、分隔线和卡片、却没有在它们的位置上换来任何东西的页面，读起来是单薄的，而盲评的评审员有理由更喜欢一个有破绽的丰富页面，而不是一个没有破绽的空页面。另一半是实质内容：更大的字号，整片的色块，这个主题世界的真实图片（找到的或绘制的），以及每个分区都承载它完整的内容。本技能的设计就是为了给你这些；不要用克制去换掉它。

在下面的命令中，`<skill>` 指本技能所在的文件夹。请从项目根目录运行这些命令，这样工作文件就会落在该目录下的 `.taste-skill/` 中。这些脚本需要 Node 22+ 以及已安装的 Chrome、Edge 或 Chromium，并且不会安装任何东西。`assets.mjs` 还需要网络访问；它不使用 API 密钥。

## 页面还是 App 界面

首先要判断这属于两类工作中的哪一类。

- **页面**是被阅读和滚动的：一个落地页、一个营销或产品站点、一个作品集、一个活动页、一家餐厅、一个单页。它遵循下面的**流程**。
- **App 界面**是在其中工作的：仪表盘、管理或分析视图、设置、账单、待处理的收件箱或队列、钱包、带筛选的列表、编辑器或构建器。它遵循 **`references/app-screens.md`**：自己的流程、自己的发牌（`draw.mjs --app`）、自己的固有规则（在那里，安静的边框、小号标签和重复面板是正常的；渐变、光晕、放在着色方块里的图标、彩虹色图表和编造的门面数字则不是）以及 `inspect.mjs --app`。开始前请完整阅读该文件；下面的页面流程不适用。

一个展示其 App 的产品站点是一个页面；其上的界面片段，在内部遵循 App 界面规则。一次性发出该产品的 App 风格，放在它自己的文件夹中，并保留页面的配色与字体：

```bash
node <skill>/scripts/draw.mjs --app --kind <kind> --brief "<the product>" --keep palette,type --out .taste-skill/app
```

并把页面展示的每一个片段（首屏的实时屏幕、某个功能的局部裁切、一张图表）都构建成该 App 的真实组成部分：用 `assets/app.css` 做它的面板、表格和控件，用 `assets/charts.js` 做它的图表，用能对得上的真实数据，说明一个结论，并按页面蓝图对待图片的方式去裁切和缩放。一个看起来像在正常工作的产品的片段，是软件页面所能拥有的最强图片；灰色条和 lorem 数字则是最弱的。当一个请求同时混合两者（一个落地页以及它背后的仪表盘）时，分别用各自的流程构建，并共用一套配色和字体。

## 流程

按顺序执行这些步骤。步骤 1–5 只需要几分钟，却决定了这个页面到底好不好。

### 1. 阅读需求与项目

弄清楚什么是真实的：主题、受众、这个页面必须促使别人去做的那一件事、技术栈、已有的品牌（配色、字体、logo），以及最重要的**真正存在哪些图像素材**：项目自己的照片或产品图、一个可以被展示的真实界面、一个你可以调用的图像生成工具，或者什么都没有。不要围绕你并不拥有的图片来做规划。"它自己什么都没有"很少真的意味着什么都没有：主题所在的城市、街道、材料和历史，都在开放档案与博物馆里，可以免费使用，只需署名（步骤 6，`scripts/assets.mjs`）。

如果需求是含糊的，就自己做判断，并用一行说明你的理解，而不是去问。只有当某个缺失的事实会阻塞工作时才提问（例如没有产品名称）。

然后在你的笔记中**给主题做一次清点**：八到十二件属于这个客户、而不属于任何竞争对手的事。查找它的名称以及这个名称的含义；它的地址、门牌号、街道和街区，以及那个地方长什么样（它的瓷砖、招牌、油漆颜色、店面上的字体、它的光线、它的天气）；需求中出现的数字（座位数、房间数、到海边的分钟数、价格、年份）；它所处的约束（每月只做一批、冬天歇业、需预约）；它的材料与颜色；它的仪式与时间（五点生起的炉火、七点的渡轮）；它那个世界里的印刷品（一张时刻表、一个标签、一张票、一块标牌）。这份清单正是步骤 4 中想法的来源。在盲测中，赢得每份需求的页面都是从这样一份清单上的某一项构建出来的（客户的名称及其含义、它所在的街道、让它成为它自己的那条约束），而落败的页面则是有好构图却只有品类想法的页面。这份清单同时也是你的图片搜索列表：其上的每一个地点、材料和印刷品，都是步骤 6 的一个查询词。

### 2. 写出论点

在任何设计之前，把页面列成一条条主张及其证据，每个分区一行，如 `references/copy.md` §1 所示。这些主张决定哪些分区存在、以什么顺序存在。删除任何没有主张的分区。这样你才能避免首屏、logo 墙、三个功能、客户证言、定价、行动召唤这种套路化的顺序。

### 3. 抽出方向

```bash
node <skill>/scripts/draw.mjs --sector <sector> --brief "<one line about the subject>" \
  --sections <roles in the order of your argument> [--tone <tone>] [--have <assets>] [--keep palette,type] \
  --options 3
```

这会发出三个方向，并打印每个方向的简短摘要。把每一个都拿去和你的清点清单对照：哪一种构图方式能承载只有这个客户才有的东西？选那一个，而不是最眼熟的那一个，并在笔记中写下一行理由。在测试中，一个随机抽到、并不适合该主题的方向，是页面薄弱最常见的原因。然后发出完整的方向表：

```bash
node <skill>/scripts/draw.mjs <the same arguments, without --options> --direction <chosen id>
```

- `--sector`：`node <skill>/scripts/draw.mjs --list sectors`。挑选最接近的那个。
- `--sections`：来自 `--list roles` 的角色（features、showcase、how-it-works、testimonial、proof、stats、pricing、faq、cta、footer、intro、about、work、gallery、list、contact）。首屏是隐含的。
- `--tone`（可选）：quiet、bold、warm、technical、playful、luxury、editorial。只有当需求明确要求某种语气时才传入。
- `--have`：真正存在的素材，以逗号分隔：`photography`（项目自己拍摄的关于该地点、人物或作品的照片）、`product-photo`（该具体产品的照片，或者一个能做出这类照片的图像工具）、`product-ui`（真实截图）、`illustration`、`video`。如果你一样都没有就省略它：这样发牌会避开依赖这些素材的构图，方向表也会说明如何诚实地填充图片位置（软件展示它自己的、用 HTML 构建的界面；一个没有照片的产品会被绘制出来，并安置在它那个世界的真实图片之间，绝不是伪造的产品图）。你会在开放馆藏中找到的图片并不属于项目自己；把它们排除在 `--have` 之外。
- `--keep palette,type`：当品牌已经固定了颜色或字体时使用。此时发牌只给出构图，你负责把品牌的值映射到各个角色上。

该命令会打印一份**方向表**。它就是这次构建的艺术指导：

- **采纳它。** 不要把它和你本来会做的那种布局混合起来。如果它让你觉得陌生，那是好事：眼熟的布局正是本技能存在的意义所在——阻止它出现。
- 只有在你能说出理由时才重抽某一个槽位（`--redraw hero | type | palette | photos | scenes | section:<role> | direction`）：它与已声明的品牌约束相矛盾，或者需要一份并不存在的素材。绝不要为了得到更舒服的东西而重抽。在报告中记录每一次重抽。
- 当抽到的某个分区无法承载真实内容时（它要对比三个方案，而实际只有一个价格；它想要五条引语，而一条也没有），不要为了迁就它而扭曲内容。用 `--alternatives <role>` 列出其他选项，挑选那个其假设与内容相符的分区，并用 `--redraw section:<role>=<id>` 采用它。
- **把配色对照主题检查一遍。** 一套抽到的配色，既是一组颜色，也是一组比例（一个底色、一种墨色、一个强调色、若干色域）。如果它的颜色与主题自身的材料相冲突（泥煤威士忌配糖果粉彩，山间小屋配霓虹），就把配色重抽一次；如果主题自身有不会认错的颜色（它的材料、它那条街的油漆、它窗外的风景），就保留抽到的比例，改从主题取色，并在报告中说明这一点。
- 随时可以用 `node <skill>/scripts/draw.mjs --show` 重新打印它。在长时间的会话中，每构建一个分区之前都重读一遍。

### 4. 找到想法

方向是一种构图方式。想法则是让这个页面属于这个主题、而不属于任何别的主题的东西。在你的笔记中写下这句话，并且在两个空都由主题自身填满之前，不要开始构建：

> 在这个页面上，**[某件属于该主题的事物]** 变成了 **[该方向所要求的装置]**。

寻找第一个空可以去的地方：

- **它的产出。** 这个事物生产什么？把真实的产出作为材料放到页面上。（一台能打印诗歌的相机，把它的文案以纸条的形式呈现。）
- **它的物件或形状。** 它在物理上是什么样子，剖面上、剪影上？把它放大，裁切，让它成为边框或那唯一的母题。
- **它的名称。** 这些字母能承载一张照片、堆成一堵墙、分到两个角落吗？
- **它的地点。** 有没有一个视角能让人想要身临其境？
- **它的仪式。** 有没有一个序列，能让页面在滚动时逐步演出？
- **它的实物。** 它的世界里已经存在什么印刷品：票、菜单、标签、收据、请柬、文件夹、说明书？
- **它的反面。** 有哪一种别的品类，拥有这一种所缺少的感觉？

用你的清点清单（步骤 1）来填第一个空，而不是用品类。**竞争对手测试：** 把最接近的真实竞争对手放进这句话里（两条街外的那家面包店、另一家橡木家具制造商、同一座山上的另一间小屋）。如果这句话依然成立，那这个想法就属于品类：一条面包属于每一家面包店；而这家店以其命名的那条街上的七扇门，只属于这一家。"干净而现代"不是一个想法。研究中评分最低的那些站点，其想法被记录为"除标准公式之外别无他物"。

**一件活的交互。** 给页面一件访客可以做的事，或者每次访问都不同的事，由这个想法生发而来：选一种木材，看看椅子用它会是什么样；输入你的名字，看看它用铸字厂的字体刻出来是什么样；设定贷款金额，读出真实的月供数字；看看小屋的炉子此刻是否点着，以及距离最后一班渡轮还有多久；选一个尺寸，看看它放在房间里是什么效果。在盲测中，每一个获胜的页面都有这样一件东西，评审员也第一个提到它。规则：它使用主题的真实内容，它能在手机上用拇指操作，它在没有脚本时有朴素的降级方案，它绝不阻塞阅读，而且它只是一件事，不是一个游乐场。它在步骤 6 中作为页面的一部分被构建，而不是在步骤 9 中作为动效被追加。

**滚动场景也承载想法。** 方向表上的滚动场景，是等待主题来认领的装置。构建之前，先从你的清点清单决定每一个场景展示什么：穿越镜头穿过的，是这家工作室自己的标题卡；那条路线，是这批货真正走的那条路；那幅展开到整屏的图片，是客人醒来时所在的房间。一个塞满"任何人都可能有"的图片的场景，只是一张屏保。

### 5. 写文字

在写标记之前，先把整个页面写成分镜式文案（纯文本），遵循 `references/copy.md`：

- **每个标题在任何宽度下都只占两行或更少。** 在定下一句话之前，先做 copy.md §2 里的算术：在有一定分量的字号下，大约 32 个字符在任何地方都是安全的。被研究的画廊站点首屏，中位数是 5 个词、32 个字符。
- 一句支撑性的话，紧接在标题之下（距其 32–48px）并与之一起显示，绝不压在首屏底部，也不被动画压住不给显示。当标题是一个名称或一个比喻时，这句话要平实地说明这个事物是什么。一个主要动作，以它实际所做的事来命名，作为首屏上的一个真实按钮。
- **首屏用大字号回答访客的第一个问题。** 对一场活动：它是什么、何时、何地（日期属于标题或第二级字号，绝不能只出现在小字里）。对一个产品：它是什么，价格或功能如何。对一个人：是谁，做什么。访客专程来看的每一个分区（阵容、菜单、房间、价格），都有自己的标题，也都在导航中占有一席之地。
- **写完整的内容。** 需求中要求的每个分区都要完整交付信息：带价格的完整菜单，每个房间各自的细节，每一位讲者与每一场演讲，价格以及它包含什么，每个真实问题的答案。单薄的分区，是一个干净的页面输给更繁复页面的最常见原因。
- 当需求留下空白时（菜名、房间名与房价、项目标题），示例细节是可以预期的，这样设计才能在完整的密度下被看到；把它们列在报告中，供客户确认。证据绝不可编造：没有客户、引语、评价、媒体报道、logo 或经营数据。

### 6. 构建，静态地

在脑中关闭动效来构建页面；一个需要动画才显得完成的页面，并没有完成。工作顺序：

1. **令牌。** 把方向表中的颜色与字体角色写成 CSS 自定义属性。下游的一切只引用令牌。`<skill>/assets/base.css` 是一个你可以起步的中性基础（reset、令牌名称、流体字号层级、网格、焦点与选中样式、动效辅助类）；它自身不带任何外观。
2. **首屏，严格按蓝图所描述的那样**，在桌面宽度和手机宽度下都做。在其他任何东西存在之前，先把大的东西做大、小的东西做小。
3. **每个分区按其蓝图来做，** 用这个项目的内容。保留几何结构，更换主题。相邻分区不得共用同一布局。**把想法带入每一个分区，** 包括定价、FAQ 和页脚：研究中（即便在好站点里）最常见的失败，是一个有辨识度的首屏后面跟着一堆套路化区块。
4. **图像素材，** 按以下优先顺序：
   1. 项目自己的；
   2. 生成的，如果你有图像工具；
   3. **来自开放馆藏的、主题世界的真实图片，** 只要存在一张诚实的就用。用 `node <skill>/scripts/assets.mjs "<query>"` 检索它们（Openverse、Wikimedia Commons、芝加哥艺术博物馆和大都会博物馆；默认只取允许商用的许可）。检索清点清单，而不是品类：它那条街在旧明信片上的样子、街区的一张老地图、它的材料特写、它的行业在版画中的样子、一件同类博物馆藏品、一张植物图版、一张星图。要把它们用大，并且带着意图去用：一张档案照片作为首屏，一幅版画放大成页面的母题，那张真实的街道地图作为联系分区。选择之前先看每一张；`--get <ref>` 会把它下载到 `assets/` 并记录其来源与许可，`--credits` 会打印用于页脚的署名行。找到的图片展示的是客户周围的世界，绝不能被当作客户自己的产品、房间、菜品、人物或团队来呈现；
   4. **用代码从主题自身绘制，** 针对那些不存在诚实图片的东西（它的物件、它的瓷砖、它的窗户、它产品的界面，做成一套一致的扁平图形语言，使用配色的真实颜色）；
   5. 方向表上抽到的照片，只在诚实的通用图片合适的地方使用（海边的房子用海），绝不作为主题的替代；
   6. 仅用字体与颜色。

   当项目有影像素材，或者有它自身流程或产品的真实图片时，首屏要展示它，并且要大（约占屏幕的 40% 或更多）。绝不要在页面上写一句话去说明图片来自哪里或它们不是什么（"这些都不是我们的吧台"）：图注只说明图片是什么，署名行小字放在页脚。一个作品为需求而虚构的作品集，要把每一件都画成该作品的一张完成定格（它自己的标题卡、配它自己的字体、一个结尾帧、一张海报），带有真实的细节，绝不画成客户产品的图标式符号。

   **底线，由检查器核查：** 页面上至少有四张真实图片，通常是六到十二张（照片、档案图像、地图、版画、影像素材、位图作品；对软件而言，裁切过的界面片段也算）。SVG 绘图不计入这条底线：为不存在图片的东西绘制，同时仍然要承载真实图片。只要存在诚实的短片，就加入一段动态影像：用 `assets.mjs --video "<query>"` 检索它，并把它作为静音循环使用，配一个封面帧。模型会跳过图片和影像，因为寻找它们是要花力气的；没有它们，页面就不合格。

   `references/imagery.md` 涵盖检索、许可与署名、视频、绘制、裁切与处理。
5. 步骤 4 的**活的交互**，要构建进它能证明该主张的那个分区（通常是首屏或预订区），带真实内容、一个适合拇指操作的手机版本以及一个朴素的降级方案。
6. **滚动场景，** 当方向表抽到它们时（第 9 节），每一个都与它所承载的分区一起：页面的重大时刻、穿过作品的镜头、展开到整屏的那张图片、在滚动下弯折的那个词。从 `<skill>/assets/scenes/` 复制共享舞台和该场景的文件，用这个项目自己的图片和文字填充场景，并设置页面的令牌，让它取得页面的外观。一个场景就是构图：它决定页面有多长、每个屏幕显示什么，所以它现在就要构建，并且在每一轮审视中都被看到，而不是最后才加上。`references/scenes.md` 说明如何把一个场景放到页面上、填充它、让它适配并检查它；`assets/scenes/demo/<id>.html` 是每一个场景的可运行示例。
7. **饱满度。** 把每一个桌面屏幕当作一张海报来看：一个主导性的东西，以及它所承载的内容。一个大部分是空底的屏幕，是一个建得不够的分区，而不是一次留白；每个页面一次有意的留白是上限，如果页面上有两个或更多近乎空白的屏幕，检查器就判定不合格。正文使用完整的墨色，字号 16px 或更大；灰色只用于次要注释。
8. **外框。** 页面在任何宽度下都只有一对相等的外边距，并且每个分区都使用页面已经设定好的宽度：当它的文字位于左半部分时，右半部分要放它的图片、它的第二栏、它的列表或它的图形，绝不能什么都不放。不对称只存在于网格内部，绝不在外框上：只有当另一侧有东西把它闭合时，才放置一处空白。页面中没有任何比半个屏幕更高的区段是完全空着的；桌面上分区之间相隔 120–240px。访客专程来看的每个分区，都以一个点名它的标题开头，首屏则用 `h1` 承载页面的标题。这些正是读者在页面看起来不对劲时最先说出的问题（"没有清晰的标题"、"莫名其妙的空白"、"所有东西都被挤到一边"），而检查器会逐项测量它们。
9. **状态与语义。** 真实的链接与按钮、可见的焦点、alt 文本、一个本身就是独立构图的手机布局。

当你需要某个决策背后的细节时，阅读 `references/type.md`、`references/colour.md` 和 `references/layout.md`；下面的法则是简写形式。

### 7. 关卡

```bash
node <skill>/scripts/lint.mjs <source files or folder>
node <skill>/scripts/inspect.mjs <url or path/to/index.html>
node <skill>/scripts/scenes.mjs <url or path/to/index.html>     # when the page has scroll scenes
```

`scenes.mjs` 会在每个滚动场景的停留进度 0、10 …… 100% 处拍照，桌面端和手机端都拍，还包括减弱动效的页面；如果方向表上有场景，`inspect.mjs` 还会把整段滚动录下来（`desktop-film-NN.jpg`）。一个从未启动、或者在桌面端静止不动的场景，是一个 `FAIL`。

`lint.mjs` 会扫描源码，查找被禁用的写法和套话。`inspect.mjs` 会在真实浏览器中以 1440、768 和 390 像素打开页面，测量它（标题行数、字号、实际加载的字体、颜色、分隔线、阴影、渐变、对比度、溢出，以及外框：边距是否相等、分区是否挤在一侧、空白区段、标题、无标题的分区、文字是否贴着屏幕边缘），并把截图保存到 `.taste-skill/inspect/`。修好每一个 `FAIL`。把每一条 `WARN` 都当作错误，除非你能用一句话向设计师为它辩护。反复重跑，直到没有 `FAIL`。不要和测量仪争辩，也不要对它隐藏东西。检查器通过一个临时本地服务器来提供本地文件；如果页面还必须能直接从文件系统打开，请在结束前以那种方式打开一次 `index.html`。

### 8. 审视

通过关卡只意味着没有被测到任何禁用项。它并不意味着这个页面是好的。打开检查器列出的截图（每一个视口，用你的图片查看器或 Read 工具），并用 `references/critique.md` 对它们进行批评：十四遍审视、按 Awwwards 加权的评分、各项上限。按它的格式把批评写下来，修好最突出的三个问题，再跑一次检查器，再看一次。最多三轮。

只凭图片判断。如果一个问题在截图中看得见，它就是真实存在的，不管代码怎么说。

### 9. 动效

现在构建动效层。它是必需的，而且不止一次淡入：检查器会统计在页面加载和滚动过程中真正移动的元素，少于八个就判定不合格（少于十六个会警告）。任何滚动场景都已经构建好了（步骤 6）；在它们周围，动效层有四个部分：

1. 方向表上点名的**标志性动作**：只有一个，并且做好（一个抽到的场景可以充当它）。
2. **每个分区各部分的入场：** 先是标题，然后是文字，再然后是图片，间隔 60–90ms 错开，带不透明度上浮 16–32px，在分区进入时触发一次。不是整块只淡入一次，也绝不能让内容在脚本失败时保持隐藏。
3. **每个控件的反馈：** 按钮、链接、卡片和那件活的交互上的按下、悬停与焦点状态。
4. **一幅动态图片：** 一段找到的短片作为静音循环，一张照片上的缓慢缩放或漂移，或者首屏图片上的滚动联动位移。

只用 transform 和 opacity；每一个动作都有 `prefers-reduced-motion` 降级方案，保留内容而去掉位移。一个会改变整屏颜色或布局的动作（按章节变色、固定叙事）属于构图的一部分，所以要在步骤 6 中构建它，并让每一轮审视都看到它。`references/motion.md` 里有令牌和经过验证的配方。然后再跑一次检查器，检查每一张截图里是否有未能出现的内容。

### 10. 汇报

在以下每一条都成立之前不要汇报；在测试中，每一条被跳过的，结果都不好：

- 在页面的最终版本上，`inspect.mjs` 在 1440、768 和 390 下显示 **0 FAIL**。
- 在最后一次改动之后，你打开过它列出的每一张截图，而不只是首屏。
- 有滚动场景时：`scenes.mjs` 在最终页面上运行无问题，并且你读过每一张图版（桌面、手机、减弱动效）。
- 一个陌生人看首屏五秒钟，就能说出这是什么、该做什么。
- 每个分区都有标题；两侧边距一致；页面中没有任何区段是空的。
- 你最后一轮的批评，已按 `references/critique.md` §4 的形式写下来。

简要地告诉用户：抽到的方向（名称与种子）以及任何重抽及其理由；想法那句话和那件活的交互；你最后一轮批评的最终得分，以及哪些地方仍然不达标；每一张找到的图片和短片及其标题、作者、许可和来源页面（`assets.mjs --credits` 会打印这份清单），以及它的署名在页面上的位置；哪些内置照片和哪些绘图被用来替代摄影（以便它们能被替换）；以及任何必须在发布前替换掉的示例内容。不要声称你做过一项你并没有运行的检查。

## 固有规则

无论方向如何，这些在每次构建中都成立。`inspect.mjs` 会测量它们。

| 规则 | 改用 |
| --- | --- |
| **标题：在任何宽度下都是两行或更少。** 每一个 `h1`–`h6`，以及首屏的主行，无论它用什么标签。 | 删词。然后加宽行长。最后才调字号。 |
| **首屏上有一个清晰的标题**，用页面唯一的 `h1`，并且每个分区都有一个标题。 | 说清楚这是什么：名称加它做什么，产品加它是为了什么，活动加其日期和地点。 |
| **外边距相等；没有分区挤在一侧，** 而屏幕的另一半空着。 | 用远侧的东西闭合每一处空白：该分区的图片、第二栏、一个列表、一个图形。 |
| **没有空白的区段** 高于约半个屏幕。 | 正常的分区间距。一次有意的留白，是一张被放置的图片或一片色块，每页一次。 |
| **陈述句就是段落。** 一句放大的引言或引语，标记为 `<p>` 或 `<blockquote>`，保持在陈述句字号（桌面上 36px 或更小，手机上 24px），长度约为 25 个词、三行。 | 比这更大它就是标题，两行规则随即适用。在盲测中，评审员会把一句 42px、占四行的句子读成一个四行标题。 |
| **不要眉标。** 标题上方没有小标签，大标题上方没有胶囊徽章，没有 "New ·" 小片。 | 把信息放进标题或第一句话里，或者干脆去掉。 |
| **不要等宽字体**，真实代码块之外一律不用。 | 使用正文字体。数字需要对齐处使用表格数字。 |
| **不要序号编号。** 不要 01 / 02 / 03，不要 (001)，不要 "Step 2"。 | 顺序由位置、大小或文字来体现。如果顺序重要，就用真正的 `<ol>`。 |
| **不要细线。** 不要发丝分隔线，不要 1px 描边盒子，不要网格线、十字准星或裁切标记。 | 用空间。用背景色调的一个层级差。用尺度的变化。用填充的形状。 |
| **不要渐变。** 不作为背景，不在按钮上，不在文字里。 | 用平涂颜色，或者一张真实照片。照片上文字底下的中性遮罩是唯一的例外。 |
| **静止的东西上不要阴影。** 不要光晕。 | 用表面之间的色调层级差。阴影只用于真正悬浮的东西：一个菜单、一个对话框。 |
| **不要 AI 助手配色。** 不要黄奶油底色配陶土色或铁锈色；不要紫罗兰或靛蓝。 | 使用抽到的配色。 |
| **不要小号大写加字距的标签。** | 使用句首大写，字号可读。 |
| **不要顶部带图标的功能卡片，不要成排一模一样的卡片。** | 使用抽到的分区蓝图。 |
| **不要玻璃拟态。** 不要背景模糊面板，不要悬浮胶囊导航。 | 一条朴素的横条：字标、几个链接、一个动作。 |
| **不要 emoji，不要渐变团块，不要装饰性形状，不要由灰色条拼成的假仪表盘。** | 用一张真实图片、一个真实界面片段，或者什么都不用。 |
| **标题中不要有被特殊设计的强调词**（斜体、衬线、变色、加下划线）。 | 一种字体，一种颜色。让文字本身承载强调。 |
| **最多两种字体，** 通常一种。 | 使用抽到的字体系统。 |

有三个地方保留它们自己的惯例，检查器不会去动：`<pre>`/`<code>` 中的真实代码（在那里等宽字体是正确的）、真实的表格和表单字段（它们可以有线），以及一个根元素带有 `data-ui` 属性的真实界面片段（产品自己的边框与菜单；见 `references/imagery.md` §7）。

老实说，为什么是这些。有些是研究测出来的：在 247 个站点中，评审团评分 7.5 或以上的站点，使用图标功能卡片的比例是 1%，而 6.5 分以下的站点是 28%；胶囊徽章 14% 对 34%；渐变 22% 对 52%；阴影 24% 对 48%；小号加字距大写 16% 对 57%。另一些则出自所有者的品味，并且与当前的画廊潮流相悖：等宽字体标签、序号编号和发丝网格，在获奖站点上实际上*比*在薄弱站点上更常见，这恰恰是生成器模仿它们的原因，也是它们如今读起来像戏服的原因。在本技能中它们被无例外地禁用。`references/tells.md` 保存着这份带时间标记的登记表。

移除装饰会留下空间。绝不要用另一种装饰去填它。用尺度去填（把主要的东西做大），用完整的内容去填，用一张为这个主题而作的图片去填，或者用一片平涂色块去填。每页最多一次，故意让它空着。

## 这门手艺的法则

简写形式。除标注为固有规则外，数字均来自该研究。

**字体**
- 两到三种字号承担可见的工作：一个非常大，一个小，中间没有。被研究站点上，标题与正文比例的中位数是 4.3；最好的远超于此（最大字号：顶级站点中位数 8.4vw，薄弱站点 5.0vw）。
- 展示字体：字距 -0.02 至 -0.05em，行高 0.85–1.05。正文：16–20px，行高 1.45–1.6，每行 45–75 个字符。
- 一个页面上五种字号是上限。一种字族是常态（被研究站点的三分之一）；两种是极限。
- 默认左对齐。最多让一个时刻居中。

**空间**
- 一个网格，一对紧凑的边距（16–32px），处处使用；大的东西一直延伸到边缘。整个页面上，文字块共享两到三条左边缘。
- 不对称在网格内部，绝不在外框上：两条外边距相等，一个偏离中心的标题，要由网格远侧的某个东西来回应。
- 分区之间的间距明显大于分区内部的任何间距：桌面上 120–240px（研究的中位数约为 240）。
- 每个分区的构图都与其相邻分区不同；没有任何一个是卡片网格。

**颜色**
- 一个底色，一种墨色，一个强调色。强调色出现在动作上，也许再加上另一处。
- 正文使用完整的墨色。一个用柔和灰色排出的页面读起来是未完成的。
- 表面之间由色调的一小步差异来分隔，绝不用一条线或一处阴影。
- 一个分区可以改变整片色域的颜色。没有任何东西淡入到别的什么东西里。

**图像素材**
- 一张主导性的图片胜过六张小图。在得分最高的站点上，首屏媒体有 68% 的情况覆盖首屏的至少一半。
- 相同的裁切比例，相同的处理方式，除非方向另有说明否则用直角（被研究站点中 73% 的媒体保持直角）。
- 没有图片，好过一个占位符、一个图标或一个抽象形状。一张为这个主题而画、用它的颜色、用心绘制的图，比这两者都好。一张找到并署名的、它那个世界的真实图片，还要更好。
- 每一张找到的图片都被下载进项目，在页面上署名，并列在报告中。没有一张被当作客户自己的来呈现。
- 任何东西都绝不叠在标题或陈述句之上（检查器会判定不合格）。

**组件**
- 按钮：平涂，一种填充色，要么直角要么全圆，一次决定（顶级站点：52% 直角，23% 胶囊；9–16px 的"柔和"圆角是薄弱站点的默认值）。大多数强有力的首屏根本没有按钮，或者只有一个。
- 导航：字标，三到五个朴素链接，一个动作。没有横条的装饰性外壳。
- 页脚是一个被设计过的收尾，而不是站点地图：在大多数强有力的站点上，名称会以整幅宽度重现。

## 特殊情况

**已有的品牌或设计系统。** 传入 `--keep palette,type`，把品牌的颜色和字体映射到各个角色上，只从发牌中取构图。固有规则依然适用；如果品牌本身要求使用某个被禁用的手法（它的 logo 坐在渐变里，它的强调色是紫罗兰），保留品牌资产，在报告中说明，并只为那一条规则向检查器传入 `--allow <rule>`。

**对已有页面或 App 界面的重设计、重样式或评审。**

1. **记录改动之前的状态。** 按现状运行项目，并把它检查到自己的文件夹里（`inspect.mjs <url> --out .taste-skill/before`，App 界面加 `--app`），同时对其源码做 lint。阅读代码：框架、样式方案（Tailwind v3 或 v4、CSS modules、styled-components、纯 CSS）、组件，以及哪些必须存活下来：路由、表单、数据、行为、品牌自己的资产。
2. **一次评审到此为止。** 用 `references/critique.md` 批评改动前的截图，连同检查器的测量数据一起列出发现，并点名最能让页面改观的三个改动。
3. **保留技术栈、内容以及能用的部分。** 不做框架或样式库迁移；在添加任何东西之前先检查依赖文件。重样式保留布局，从抽到的方向中取字体、颜色和组件（品牌固定了什么就 `--keep` 什么）；重设计则抽出一个完整方向，并在现有组件内部按它的蓝图重建各个分区。无论哪种方式，都从流程的步骤 2 开始，用页面的真实内容继续。
4. **工作顺序，以最小风险取得最大效果：** 字体（字族与尺度）、颜色（一个底色、一种墨色、一个强调色）、外框（边距、分区节奏、首屏上的标题和每个分区上的标题）、状态（悬停、焦点、加载、空、错误），然后用抽到的蓝图替换那些套路化组件（图标卡片、胶囊徽章、渐变团块、卡片网格）。
5. **证明它。** 再次检查并输出到 `.taste-skill/after`，在每个宽度下对比改动前后，点遍每一个之前能用的链接、表单和菜单，并把改动前后的测量数据并排汇报。

**一个组件或单个分区，而不是一个页面。** 除非没有可遵循的方向，否则跳过发牌。与周围的设计保持一致，应用固有规则和法则，并且仍然检查结果。

**没有结账，没有表单后端。** 当需求指明了真实去处时，主要按钮就指向那里。否则它打开一封带有写好的主题与正文的邮件（`mailto:`，并填入访客的选择），或者，对商店而言，它指向 `#checkout`，而报告要说明它必须在发布前接好线。绝不伪造支付表单。

**没有 Chrome 或 Node 22。** 运行 `lint.mjs`（Node 18+），用你手头有的任何浏览器工具截图，并对那些截图做批评。在报告中说明检查器无法运行。

**没有网络。** 如果 `assets.mjs` 无法连接到任何来源，就自己绘制图片，并在报告中说明开放馆藏无法检索。
